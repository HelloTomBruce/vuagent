# Token 预算与上下文治理

> 长会话失控是 Agent 生产系统最常见的隐形杀手。如果不做严格治理，多次工具调用后单次请求可能瞬间消耗几十万 Token，不仅响应奇慢，还会产生惊人的费用甚至触发模型的 Context Length Exceeded 崩溃。

---

## 为什么“按轮次保留历史”不可行？

许多初级 Agent 系统习惯采用类似“只保留最近 10 轮对话”的策略。这在 Agent 场景下是完全不可靠的：
* 普通用户的一问一答可能只消耗 200 Token；
* 但模型调用一次 `glob`、`fs_read` 或数据库查询，返回的 JSON 结果可能高达 **30,000 ~ 50,000 Token**；
* 轮次之间的 Token 体量差异可达 **2 到 3 个数量级**。按轮次切分，完全无法预测上下文何时会被撑爆。

---

## 基于真实 Token 预算的滑动压缩器

`@vuagent/server` 坚决以 **Token 口径（Tokenizer 计数与精确估算）** 作为唯一预算依据：

```text
 ┌────────────────────────────────────────────────────────────────────────┐
 │ 上下文窗口总容量 (例如 128K)                                             │
 ├────────────────┬───────────────────┬───────────────────────────────────┤
 │ 系统提示与工具 │  历史摘要折叠区   │   最近轮次滑动窗口区 (完整保留)    │
 │ (高优先级保留) │  (压缩为几行要点) │   (保证当前任务上下文连贯性)       │
 └────────────────┴───────────────────┴───────────────────────────────────┘
```

### 1. 自动滑动窗口与摘要折叠
* **阈值控制**：当上下文总 Token 达到配置的安全水位（如总窗口的 70%）时，压缩器自动介入；
* **摘要折叠**：更早的轮次被抽取出关键目标、核心约束与已完成结论，转换为轻量的摘要消息；被折叠的原始轮次彻底退出上下文；
* **最近轮次保真**：最近数轮的核心交互与当前未决工具调用完整保留，确保 Agent 的 ReAct 推理逻辑不断层。

### 2. 工具超长输出截断
针对 `grep`、`bash` 或大数据量查询工具，服务端在结果进入上下文前设置硬性字数截断阀（如单条结果超 8KB 自动截断并附带提示：“内容已截断，请细化检索条件”），防止单次工具调用击穿上下文。

### 3. 多模态附件（图片）估算与降级
* 输入多模态图片按每张图约 1,000 Token 进行预算估算；
* 当历史被压缩折叠时，历史轮次中的图片数据自动降级为文本占位符 `[图片]`，释放大量上下文，避免多图重放导致的内存膨胀。

## 实时三段水位与前端仪表展示

服务端在每一步均下发 `usage` 事件，将上下文拆解为三段：
1. **`system`**：系统提示词与全局规则消耗；
2. **`history`**：对话历史与上下文占用；
3. **`tools`**：工具定义与执行结果占用。

前端组件 `VaContextWindow` 可以直接消费这三段数据，在界面上直观展示彩色的分段进度条，让用户和管理员对当前上下文的水位一目了然。
