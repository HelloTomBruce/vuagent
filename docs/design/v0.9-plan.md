> 状态：**设计待评审**（范围已与用户对齐：MCP / web_search / L2 组件家族 + 技术债；新功能方向由用户拍板，「模型运维仪表盘 / resume 转正 / fallback 链」明确否决，归档不进 0.9）。

## 1. 背景与动机

1. **MCP（Model Context Protocol）** 已是外部工具接入的事实标准（Anthropic 牵头、主流客户端跟进）。vuagent 当前工具面固定为 18 个内置工具，用户无法挂接自有工具（数据库、内部 API、浏览器自动化）。接入 MCP = 一次接入、长尾全解。
2. **web_search** 在 `web_fetch` 的工具描述里已预留语义（「需要实时信息请配合 web_search（如已配置）」）但从未实现——查文档 / 查 issue / 查依赖版本是工程任务高频动作，只有 `web_fetch`（给定 URL）覆盖不了「不知道 URL」的场景。
3. **L2 契约基建已上线但组件只有 1 个**（ui_form）。信封契约（submit/cancel/patch）、`deriveResultSchema` 动态推导、语义摘要、progressive 流式禁用四条管道全部组件无关——加组件的边际成本只剩「声明数据 + 前端渲染」。
4. **到期承诺**：v0.7-plan §13 明确 `VUAGENT_CHECKPOINT_STORE=inline` 回退「保留一个版本（0.8.0 移除）」，0.8.0 已发未移，0.9.0 是兑现窗口。
5. **实测 UX 缺陷**（0.8.0 真实供应商走查发现）：无工作区时首页点「发送」静默无效（无提示无请求）；连通性测试结果以 toast 呈现几秒即逝且常被弹窗遮挡。

## 2. W1：MCP 客户端支持

### 2.1 总体架构

```
~/.vuagent/config/mcp.json          ← 连接配置（唯一事实源，文件形态）
        │ 启动时加载 / 运行中 watch
        ▼
McpHostService（server 单例，Facade）
  ├─ 连接生命周期：懒启动 / 指数退避重试 / 崩溃重启 / 关停断连
  ├─ transport：stdio（子进程）优先；streamable HTTP 次之（v0.9 二选一都做或只做 stdio，见 §7 待拍板）
  ├─ 工具发现：tools/list → 转换为 HarnessTool
  └─ 调用代理：registry.execute → MCP tools/call
        │ Adapter 转换（mcp__<server>__<tool> 命名空间）
        ▼
现有 ToolRegistry.register()        ← 复用既有校验 / 超时 / HITL / 启停全链路
```

**核心决策：MCP 工具是 Adapter，不是平行体系。** 转换为 `HarnessTool` 后 `register()` 进现有 registry，从此享受既有的一切：TypeBox/参数闸门、60s 超时沙箱、`toolConfigRepo` 启停（设置 → 工具页自动出现）、`disabledNames` 可见性、HITL 审批、ops 台账。**不存在绕过 registry 的执行通道。**

### 2.2 关键设计决策

| 决策点 | 选择 | 理由 |
|---|---|---|
| 工具命名 | `mcp__<server>__<tool>` | 对齐 Claude Code 惯例；前缀命名空间从根上杜绝与内置工具/其他 server 的重名冲突 |
| 参数 schema | `Type.Unsafe` 包装原始 JSON Schema（不转 TypeBox） | `validateParams` 对无 `Kind` 符号的 schema 既有「放行」向后兼容路径（tool-registry.ts:127）；参数校验交 MCP server 端执行——**诚实放行优于假装校验**；`sanitizeSchemaForModel` 继续清洗 `$ref` 保模型网关兼容 |
| 审批语义 | 新增 per-server `trust: "confirm" \| "trusted"`，缺省 `confirm` | 对齐仓库权限哲学：默认审批、显式信任。`trusted` 时 `requiresApproval: false`，`confirm` 时走既有 HITL |
| riskLevel | 缺省 `"medium"` | 与内置工具基线一致 |
| 配置形态 | `~/.vuagent/config/mcp.json` 文件（非 settings repo） | 对齐 MCP 生态惯例（Claude/Cursor 均为 json 配置文件），便于拷贝/版本管理；v0.9 设置页只读展示 + `doctor` 报告连接状态，编辑器 UI 留 0.10 |
| resources / prompts | **v0.9 不做**，只做 tools | 切界明确；resources 需要「挂载进上下文」的新语义，属独立工作流 |
| 启停 | 沿用 `toolConfigRepo`（按工具名） | MCP 工具名带命名空间，天然不与内置冲突 |

### 2.3 McpHostService 生命周期

- **懒启动**：server 启动只读配置不连接；首次 `tools/list`（registry 组装 definitions 前）或首次调用时连接。冷启动零开销。
- **重试**：连接失败指数退避（1s/4s/16s，封顶 60s），重试期间该 server 的工具从 definitions 隐藏（`hideTools` 管道，配置推导语义）并在 `doctor` 标红。
- **listChanged**：MCP server 可推送工具变更通知 → 增量 `register`/`remove`（不重建 registry，Map 单线程无并发问题）。
- **子进程卫生**（stdio）：McpHost 持有 ChildProcess 引用，server SIGINT/exit 时 `kill` 进程树；`doctor` 新增检查——残留 mcp 子进程报告。**僵尸进程是 stdio transport 的头号风险，生命周期必须绑定 owner。**
- **超时**：调用超时沿用 registry 缺省 60s（可按 server 配置 `timeoutMs` 覆盖）。

### 2.4 测试策略

- 协议层：用 MCP 官方 SDK 的 InMemory transport 构造 mock server（不需要真子进程）覆盖：工具发现→注册、调用代理、错误传播、listChanged 增量、连接失败降级。
- 生命周期：server 关停 → 子进程回收（真 stdio 子进程，集成测试 1 条）。
- 安全：`trusted`/`confirm` 两档审批行为、工具名命名空间冲突防护。

## 3. W2：web_search 工具

### 3.1 设计

```
SearchProvider 接口（策略模式）
  search(query, opts) → { title, url, snippet }[]
  ├─ TavilyProvider  （tavily.com，key 制）
  └─ BraveProvider   （search.brave.com API，key 制）
```

- **工具声明**：`web_search`（`packages/server/src/tools/web/`，与 web_fetch 同文件族）。参数：`query`（必填）、`max_results`（≤10 缺省 5）、`topic`（general/news）、`time_range`（可选）。
- **key 配置**：env `TAVILY_API_KEY` / `BRAVE_API_KEY` 优先；设置页「模型与 API」旁新增一节可存（settings repo，掩码回显沿用 apiKey 模式）。provider 选择缺省 `tavily`。
- **无 key = 工具隐藏**：走 `hideTools` 管道（`finish_task` 的 finishTaskMode=off 先例——配置推导语义，不进 `/api/tools` 启停）。模型看不到不存在的工具，不会幻觉调用。
- **安全边界（职责分离）**：
  - 搜索 API 是**出站 HTTPS 到固定厂商域名**（api.tavily.com / api.search.brave.com），无用户可控 URL → 无 SSRF 面，不接 `assertFetchableUrl`。
  - 结果只回 **snippet + URL**，**不自动 fetch**——用户点开或模型另行 `web_fetch`（该路径已有完整 SSRF 防护）。搜索结果不绕过任何既有防线。
- **provider 实现**：直接 `fetch` 各家 REST API（无 SDK 依赖），50 条结果字符截断沿用 WEB_FETCH 的截断契约风格。

### 3.2 测试策略

Provider 接口 mock 覆盖：正常返回 / HTTP 错误 / 超长截断 / key 缺失时工具隐藏。真实厂商 API 不进 CI（1 条手动验收脚本即可）。

## 4. W3：L2 组件家族

### 4.1 三个组件

| 组件 | 入参（模型给） | 回传（resultSchema 推导） | 场景 |
|---|---|---|---|
| `ui_option_picker` | `options[]: {id,label,description?,recommended?}` + `multiple?` | `{ selected: string[] }`（单选归一为长度 1 数组） | 方案拍板、技术选型 |
| `ui_wizard` | `steps[]: {title, fields[]}`（fields 复用 ui_form 的 FormField 类型） | `{ values }`（全部步合并，schema 按 steps 推导） | 多步配置采集 |
| `ui_data_table` | `columns[]: {key,label,type?}` + `rows[]`（初始行，可空） | `{ values: Record<key,unknown>[] }` | 批量结构化数据采集（映射表、名单） |

### 4.2 设计原则

- **wizard 是「一个 L2」不是「多次 L2」**：全量渲染、前端分步展示、一次挂起一次回传。不做步间服务端挂起——那会把 L2 的「一次采集」语义复杂化（超时语义、部分提交、patch 归属全部变含糊），且 L3（ui_agent_plan）已覆盖「多轮渐进协作」场景，两者语义边界保持清晰。
- 全部走 `deriveResultSchema` 动态推导（`liftFormResultSchema` 的既有模式）；语义摘要管道复用（「用户从 4 个方案中选定 1 个」）；progressive 流式禁用约束（契约 §6）沿用——args 未齐禁用提交控件。
- `timeoutMeaning: "cancel"`（与 ui_form 一致）。
- 前端：`packages/ui/src/runtime/registry.ts` 注册 + console 渲染组件，复用 VaForm 体系。

### 4.3 测试策略

沿用 L2 信封契约测试模式：deriveResultSchema 各形态（单选/多选/空 options/steps 合并/columns 类型）、边界校验回传、超时 cancel、progressive 禁用。

## 5. W4：技术债与 UX 修复

### 5.1 inline 回退开关移除（到期承诺）

- **删除面**：`turn-persistence.ts` 的 `resolveCheckpointStoreMode()` 与 `storeMode` 分支（`CheckpointStoreMode` 收窄为 `"split"`）、`opts.checkpointsRepo` 缺省回落 inline 的构造宽松化（签名改为必选）、相关 env 文档（v0.7-plan §13 / cli-data-dir-architecture 真值表）。
- **保留面**：inline **形态数据的读取与惰性迁移**完整保留（0.7 已实现）——删的是「写 inline」路径，不是「读 legacy」。用户 0.6 老库升级链路不受影响。
- **连带**：所有构造 TurnPersistence 的单测改传 checkpointsRepo（真仓储或内存假体）；doctor 里如有 inline 模式提示一并清理。

### 5.2 无工作区静默失败（UX 缺陷）

现状：首页无任何工作区时，composer 输入 + 点「发送」无提示、无请求（实测三次确认）。
修法：无工作区时发送按钮禁用 + composer 上方空态引导条（「选择或新建工作区后开始」+ 按钮）。不发无主消息、不自动建工作区（保持「工作区是显式决策」的既有语义）。

### 5.3 探测结果易逝（UX 缺陷）

现状：连通性测试结果以全局 toast 呈现，几秒消失且常被设置弹窗遮挡（实测三次截图才抓到）。
修法：最近一次探测结果**内联显示在模型行**（成功：`✓ 首响应 619ms · 2 分钟前`；失败：⚠ 一行错误摘要，悬浮看全量），进程内存态即可（不落库、面板重开清空）。toast 保留（全局可见性）但不再是唯一呈现。

## 6. 架构健康度与设计模式评估

### 6.1 健康度基线：本计划不引入新范式

0.7~0.8 建立的结构资产全部复用：单一事实源（preset 表）、Registry 模式（工具）、信封契约（交互 L0-L3）、配置中心（security）、`hideTools`/`disabledNames` 双通道可见性、HITL 审批闸门。三个新功能都是「往既有骨架上挂东西」，不是「并排造第二套骨架」——这是本计划最重要的架构约束，也是可维护性的保证。

### 6.2 MCP：最大风险项的逐项评估

| 风险 | 评估 | 缓解 |
|---|---|---|
| 逃生舱（绕过沙箱） | **无**。MCP 工具转换为 HarnessTool 进 registry，执行路径与内置工具逐字节同一（校验/超时/HITL/台账） | Adapter 模式的结构保证，而非约定 |
| 第三方子进程管理 | stdio transport 的真实风险：孤儿进程 | 生命周期绑定 owner（§2.3）+ doctor 检查；这是 W1 验收门槛之一 |
| 工具名冲突 | 内置/MCP server 间重名 | 命名空间前缀从根上杜绝（`mcp__<server>__`） |
| 第三方 schema 兼容 | MCP inputSchema 是裸 JSON Schema | 不转 TypeBox（诚实放行）+ `sanitizeSchemaForModel` 清洗 `$ref`（既有函数复用） |
| 网络面 | stdio = 本机进程；streamable HTTP = 出站到用户配置的 URL | 配置文件是用户显式写的（威胁模型同 `--console-dir`），不走 `assertFetchableUrl`（它是给「模型给的 URL」用的，语义不同） |
| 依赖 | `@modelcontextprotocol/sdk`（官方 TS SDK） | 新增运行时依赖进 cli/server；体积影响在 check-pack 门禁观察 |

**设计模式落点**：Adapter（MCP↔HarnessTool）、Facade（McpHostService 收口连接管理）、Strategy（transport 可插）、Observability（doctor 报告连接状态）。全部是仓库已在用的模式，无新范式。

### 6.3 L2 家族：抽象复用度是设计正确性的证据

三个组件的增量 = 「声明数据 + 前端渲染」。deriveResultSchema / 语义摘要 / 信封校验 / progressive 禁用四管道零改动复用——如果实现中发现某管道需要 if(component) 分支，即为抽象泄漏信号，回头修抽象而不是加分支。wizard「一次挂起」决策（§4.2）是保持 L2/L3 语义边界的关键，不做步间挂起。

### 6.4 inline 移除：删除面清单化

删除面已列全（§5.1），保留面（legacy 读）有 0.7 惰性迁移测试兜底。风险最低的一项，放 M1 先做。

### 6.5 兼容性与发布面

- 无破坏性 API 变更；`opencode-go` 预设（pending）随本版发 → protocol minor。
- MCP 是纯新增面（无 key/无配置时零行为变化——懒启动 + 空配置 = 不连）；web_search 无 key 时工具隐藏。**零配置用户的 0.9.0 与 0.8.0 行为差异 = inline 移除（无感）+ 两个 UX 修复。**
- 新增运行时依赖：`@modelcontextprotocol/sdk`；web_search 不加 SDK。

### 6.6 测试策略总览

延续「真断言 + 变异验证」的仓库标准：MCP 用 InMemory transport（不依赖真子进程进 CI）、L2 用信封契约测试、inline 移除后跑全量 checkpoint 测试族确认无回归。发布前门禁照旧（typecheck/test/build/registry/llms/check-pack/cli:smoke）。
